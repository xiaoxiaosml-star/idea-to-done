# 05｜解决方案设计：先解决最核心的问题，不要把所有功能都塞进去

> 核心问题：针对已经验证的问题，我准备用什么方式创造可感知的价值？
>
> **什么时候回到本章**：准备给方案加新功能、发现承诺口径说不清，或者客户需求开始漂移、范围越来越模糊的时候。

## 一句话价值主张

> 我为【谁】，在【什么场景】解决【什么问题】，通过【什么方式】，主要带来【什么可感知结果】。

差异不是一定要“全世界没人做过”。早期更重要的是：更适合这批用户、更快、更方便、更可信、更低风险或更清楚。

## 从结果倒推方案

先写用户想得到的变化，再写实现它所需的最少环节。

不要从功能列表开始。

## 必须区分三层

- **核心结果**：用户真正购买的变化。
- **交付机制**：你怎样帮助他获得结果。
- **包装形式**：APP、课程、咨询、商品、社群、门店等。

包装形式可以变，核心结果不要轻易混淆。

## 解决方案假设表

至少列出：

- 用户为什么会选择它；
- 用户为什么可能不选；
- 哪个环节最难交付；
- 哪个假设一旦错，整个方案就不成立；
- 哪部分可以先人工完成。

## 写清承诺边界

解决方案设计时同时写三件事：

- **我能承诺什么**：可控制的过程、交付物、服务标准；
- **我不能承诺什么**：受用户、市场、运气等外部因素影响的最终结果；
- **用户必须做什么**：提供材料、执行建议、配合时间等。

不要为了成交把不可控结果包装成保证。

## 服务范围、变更与验收
服务/咨询/代运营/外包必须提前写清包含项、不包含项、修改次数、中途加需求的处理、完成标准和超范围报价。范围模糊会在交付阶段吃掉利润。

## 本章工具

- `tools/05-需求证据表.md`——按证据等级（口头认可 < 主动询问 < 留资/预约 < 试用投入 < 订金 < 付款 < 复购/推荐）逐条记录证据支持或削弱哪个假设，并主动寻找反对证据
