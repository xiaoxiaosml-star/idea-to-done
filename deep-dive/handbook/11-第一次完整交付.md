# 11｜第一次完整交付：收钱只是开始，兑现才是生意

> 核心问题：用户付钱以后，我们能否稳定、合规、可承受地兑现承诺？
>
> **什么时候回到本章**：首单交付前后、用户不满意却说不出哪里不对，或者开始怀疑这件事能不能不靠临场发挥重复做的时候。

## 交付要记录五类事实

1. **结果**：用户实际得到了什么？
2. **过程**：哪里顺、哪里卡？
3. **成本**：实际花了多少钱和时间？
4. **异常**：售后、返工、投诉、延期来自哪里？
5. **后续**：愿不愿复购、推荐或继续使用？

## 预期差比功能缺失更危险

很多不满意不是“产品差”，而是购买前承诺与实际体验不一致。

因此要对照：

> 我卖的时候说了什么？用户以为什么？最后得到什么？

## 创始人也要复盘

如果每服务一个用户都把自己耗空，即使用户满意，模式也未必可持续。

## 比较“预计”与“实际”

首批交付必须对照：

| 项目 | 预计 | 实际 | 偏差原因 |
|---|---:|---:|---|
| 交付时间 | | | |
| 直接成本 | | | |
| 沟通次数 | | | |
| 售后/返工 | | | |

早期最有价值的数据之一，就是“我原来以为”和“实际发生”之间的差。

## 持续价值业务不能只看交付完成
订阅、课程、社群、软件要看：付款 → 激活 → 使用 → 价值实现 → 留存/续费。记录首次关键动作、使用频率、停止使用时间和离开原因。

## 常见错误

- 交付前不写清范围和验收：范围模糊会在交付阶段吃掉利润，修改一次加一项，最后白做。收钱前用 `11A-服务范围与验收表` 写死包含项、修改次数和验收标准。
- 只记结果不记成本：不知道每单实际花了多少钱和时间，就无法判断模式值不值得重复。结果、过程、成本、异常、后续五类事实都要记。
- 把用户满意当模式成立：每服务一个用户都把自己耗空，即使满意也不可重复。创始人也要复盘自己的承载力。
- 订阅、社群、软件只看“交付完成”：首单不代表持续价值，付款后没人用照样留不住。要追激活、使用、留存和离开原因。
- 用户不满意就归咎于功能缺失：很多不满意来自预期差——卖的时候说了什么和用户以为的不一致。先对照“我卖的—用户以为的—实际得到的”。
