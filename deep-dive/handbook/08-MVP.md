# 08｜MVP：不要先证明你能做出来，先证明别人需要

> 核心问题：最少做什么，就足以验证当前最危险的假设？
>
> **什么时候回到本章**：想把方案做成“完整版”再推出、当前最危险的假设发生了变化，或者一次验证结束后要设计下一版最小方案的时候。

## MVP 不是“烂产品”

MVP 是**最小可验证方案**。它可以粗糙，但不能欺骗；可以人工，但必须真的交付核心价值。

## 五种常见降级

- 软件 → 表格 + 人工服务
- 平台 → 人工撮合
- 完整课程 → 一次工作坊
- 大批库存 → 样品 / 预售
- 门店 → 快闪 / 摆摊 / 店中店

## 先找最危险假设

不是所有东西都要同时验证。

如果最大未知是“有没有人付钱”，就先验证付款，不要先优化 UI。

如果最大未知是“能不能交付结果”，先服务少量用户，不要先投广告。

## MVP 底线

- 不虚构功能；
- 不伪造用户；
- 不隐瞒关键限制；
- 不用“测试”作为伤害用户权益的借口；
- 涉及法律、安全、健康、资金等高风险领域，先满足必要合规要求。

## 本章工具

- `tools/09-MVP设计表.md`——锁定当前最危险假设，定最少核心价值、明确不做什么、哪些先人工、预算期限和成功/失败判断

## 通关条件

- [ ] MVP 只保留验证核心假设所需部分
- [ ] 制作周期和预算有上限
- [ ] 用户能真实接触并获得核心价值
- [ ] 知道这版明确不做什么
